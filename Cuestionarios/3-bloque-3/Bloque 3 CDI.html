Base de datos relacional

En una frase: una base de datos relacional guarda los datos en tablas (como hojas de cálculo con reglas) y conecta unas tablas con otras mediante columnas que comparten valores.

  • Base de datos relacional → conjunto de datos almacenados en una o más tablas.
  • Cada tabla está organizada en filas (registros) y columnas (atributos).
  • Se pueden establecer relaciones entre las tablas por medio de columnas (atributos).

Diapositivas 3–4

Clave primaria y clave foránea

En una frase: la clave primaria es el «DNI» de cada fila (no se repite); la clave foránea es una columna que guarda el DNI de una fila de otra tabla para enlazarlas.

  • Las relaciones entre tablas se explicitan por medio de:
    • Clave primaria: columna o combinación de columnas que identifican unívocamente a las filas de una tabla.
    • Clave foránea (también conocida como clave externa): columna o combinación de columnas en una tabla que hacen referencia a la clave primaria de otra tabla.
Imagen descrita Las diapositivas 6–7 muestran el modelo de la biblioteca en MySQL Workbench. En la primera versión hay tres tablas: LIBRO (clave primaria IdLibro), USUARIO (clave primaria IdUsuario) y PRESTAMOS, cuya clave primaria es IdPrestamo y que tiene dos claves foráneas: IdLibro e IdUsuario. En la segunda versión se añade la tabla AUTOR (IdAutor, Nombre, Nacionalidad) y LIBRO pasa a tener una clave foránea IdAutor; USUARIO incluye NIF, NumUsuario, Nombre, Dirección y Teléfono.
Para qué sirve La tabla PRESTAMO no repite el título del libro ni el nombre del usuario: solo guarda sus identificadores. Así cada dato vive en un único sitio y, si cambia la dirección de un usuario, se actualiza una sola fila.

Diapositivas 4, 6, 7

Representación de relaciones (notación «pata de gallo»)

En una frase: los símbolos al final de cada línea dicen cuántas filas de una tabla pueden estar relacionadas con una fila de la otra (cardinalidad).

Cómo se lee El símbolo más cercano a la tabla indica el máximo (raya = uno, «pata de gallo» = muchos) y el siguiente el mínimo (círculo = cero, raya = uno). En la biblioteca: un libro tiene «cero o muchos» préstamos, y cada préstamo corresponde a «uno y solo un» libro.

Lenguaje SQL

En una frase: SQL (Structured Query Language) es el idioma con el que se crean tablas, se guardan datos y se les hacen preguntas en una base de datos relacional.

  • Lenguaje estándar para utilizar y mantener bases de datos relacionales.
  • Utilizado en los principales gestores de bases de datos relacionales.
    • Existen pequeñas variaciones (dialectos) dependiendo del gestor.
  • Se dispone de conectores para los lenguajes más utilizados: Java, C++, Python, …
  • Dependiendo del gestor se pueden manejar usuarios y asignar privilegios.
Ejemplos de gestores MySQL, PostgreSQL, SQLite, Oracle, SQL Server. Los ejemplos de la asignatura usan sintaxis MySQL (p. ej. AUTO_INCREMENT).

Diapositiva 8

Manejo de bases de datos y tablas: CREATE, USE, DROP

En una frase: primero se crea la base de datos y se «entra» en ella; después se definen sus tablas indicando columnas, tipos, claves y restricciones.

Bases de datos

  • Una base de datos se crea con CREATE DATABASE nombre.
  • Para hacer uso de una base de datos: USE nombre.
CREATE DATABASE Biblioteca;
USE Biblioteca;

Tablas

  • Se crean tablas con CREATE TABLE nombre (columnas).
  • Al crear una tabla se especifican aspectos como:
    • Nombre de la tabla.
    • Para cada columna: nombre y tipo de datos; valor por defecto (DEFAULT valor); si puede tomar valor NULL; si es un campo de auto-incremento.
    • Claves primarias y foráneas.
    • Índices.
  • Asignación de clave primaria: indicar PRIMARY KEY en la definición de la columna, o bien PRIMARY KEY (nombre columna) al final.
  • Creación de claves foráneas: FOREIGN KEY (columna) REFERENCES tabla(columna clave primaria).
  • Eliminar una tabla: DROP TABLE <nombre de tabla>;
  • Evitar errores al crear tablas existentes o borrar tablas inexistentes → creación/eliminación condicional: CREATE TABLE IF NOT EXISTS …; y DROP TABLE IF EXISTS …;
-- Clave primaria en la columna
CREATE TABLE TABLA1(
  id INT PRIMARY KEY AUTO_INCREMENT,
  nombre VARCHAR(80) NOT NULL,
  direccion VARCHAR(200) NOT NULL,
  telefono VARCHAR(9) NULL
);
-- Clave primaria al final
CREATE TABLE TABLA1(
  id INT AUTO_INCREMENT,
  nombre VARCHAR(80) NOT NULL,
  direccion VARCHAR(200) NOT NULL,
  telefono VARCHAR(9) NULL,
  PRIMARY KEY (id)
);
-- Clave foránea: provincia apunta a la tabla PROVINCIA
CREATE TABLE TABLA1(
  id INT AUTO_INCREMENT,
  nombre VARCHAR(80) NOT NULL,
  direccion VARCHAR(200) NOT NULL,
  provincia INT NOT NULL,
  telefono VARCHAR(9) NULL,
  PRIMARY KEY (id),
  FOREIGN KEY (provincia) REFERENCES PROVINCIA(id)
);
Nota En la captura de la diapositiva aparece «id INT BibliotecaAUTO_INCREMENT»: es una errata del editor; lo correcto es id INT AUTO_INCREMENT. Para que la clave foránea funcione, la tabla PROVINCIA debe existir antes y su columna id debe ser su clave primaria.

Diapositivas 9, 10, 12, 13, 14

Tipos de datos y valor NULL

En una frase: cada columna solo admite un tipo de dato (número, texto, fecha…), y NULL significa «no hay valor», que no es lo mismo que 0 ni que texto vacío.

  • Las columnas tienen un tipo de datos asociado.
  • Principales grupos de tipos de datos:
    • Numéricos: INT, TINYINT, FLOAT, DOUBLE, …
    • Cadenas de caracteres (texto): VARCHAR(N), TEXT, JSON, …
    • Fechas / horas: DATE, TIME, DATETIME, …
    • Otros: BINARY, …
  • Los tipos de datos concretos varían según el gestor de bases de datos.
  • Valor especial NULL: ausencia de valor.
Aclaración VARCHAR(N) es texto de longitud variable de como máximo N caracteres. NOT NULL obliga a dar un valor; NULL lo permite vacío. Para comprobar nulos en una consulta se usa IS NULL, no = NULL.

Ejemplo completo: tablas de la biblioteca

Qué hace: borra las tablas si existen (en orden inverso a las dependencias) y crea LIBRO, USUARIO y PRESTAMO con sus claves.

USE CienciaDatos_BD;

-- Borrar tablas
DROP TABLE IF EXISTS PRESTAMO;
DROP TABLE IF EXISTS LIBRO;
DROP TABLE IF EXISTS USUARIO;

-- Crear tabla LIBRO
CREATE TABLE IF NOT EXISTS LIBRO (
  IdLibro INT PRIMARY KEY NOT NULL AUTO_INCREMENT,
  Titulo VARCHAR(100) NOT NULL,
  Autor VARCHAR(100) NOT NULL,
  ISBN INT NULL,
  Editorial VARCHAR(60) NULL);

-- Crear tabla USUARIO
CREATE TABLE IF NOT EXISTS USUARIO (
  IdUsuario INT PRIMARY KEY NOT NULL AUTO_INCREMENT,
  DNI INT NOT NULL,
  Nombre VARCHAR(100) NOT NULL,
  Dirección VARCHAR(200) NULL,
  Teléfono VARCHAR(20) NULL);

-- Crear tabla PRESTAMO
CREATE TABLE IF NOT EXISTS PRESTAMO (
  IdPrestamo INT PRIMARY KEY NOT NULL AUTO_INCREMENT,
  IdLibro INT NOT NULL,
  IdUsuario INT NOT NULL,
  FechaPrestamo DATE NOT NULL,
  FechaDevolución DATE NOT NULL,
  FOREIGN KEY (IdLibro) REFERENCES LIBRO(IdLibro),
  FOREIGN KEY (IdUsuario) REFERENCES USUARIO(IdUsuario));
Por qué ese orden PRESTAMO se borra primero porque depende de LIBRO y USUARIO (sus claves foráneas apuntan a ellas); si se borrase antes LIBRO, el gestor daría error de integridad referencial.

Inserción de registros: INSERT INTO

En una frase: INSERT INTO añade filas nuevas a una tabla.

  • Se insertan registros nuevos (filas) en tablas mediante INSERT INTO:
    • Se puede insertar una o más filas en una única sentencia.
    • Se puede especificar qué columnas se proporcionan y en qué orden (por defecto, se deben proporcionar todas y en el mismo orden en que se definieron al crear la tabla).
  • Se puede omitir el valor de algunas columnas:
    • Columnas autoincrementales: reciben automáticamente un valor numérico único que se incrementa a medida que se insertan filas en la tabla. Se suelen utilizar como clave primaria.
    • Otros tipos de columnas: reciben el valor por defecto definido para dicha columna, o NULL si no se ha definido dicho valor.
INSERT INTO <tabla>
(<columna_1>, <columna_2>, <columna_3>)
VALUES
(<valores_fila_1>),
(<valores_fila_2>)

Diapositivas 17–21

Modificación de registros: UPDATE

En una frase: UPDATE cambia valores de filas que ya existen; WHERE decide cuáles.

  • Se actualizan valores mediante la sentencia UPDATE.
  • Se indica qué columnas se desea cambiar y su nuevo valor. El resto de las columnas mantendrán su valor.
  • Con la cláusula WHERE se indica qué registros se modifican (todos si se omite esta cláusula).
UPDATE <table>
SET <Columna_1> = <Expression_1>,
    <Columna_2> = <Expression_2>
WHERE <condición>
UPDATE USUARIO
SET Dirección = "Las Palmas"
WHERE DNI = 12345;

UPDATE USUARIO
SET Dirección = "Telde",
    Teléfono = "999123456"
WHERE DNI = 78235
Resultado José Hernández (DNI 12.345) pasa a tener Dirección «Las Palmas»; María Pérez (DNI 78.235) pasa a «Telde» con teléfono 999123456. El resto de usuarios sigue con NULL.

Borrado de registros: DELETE

En una frase: DELETE elimina filas; sin WHERE las elimina todas.

  • Se eliminan registros en una tabla mediante la sentencia DELETE.
    • Se indica el nombre de la tabla y la condición que deben cumplir las filas a eliminar.
    • MUY IMPORTANTE: si no se indica condición, se eliminan todos los registros de la tabla.
DELETE
FROM <tabla>
WHERE <condición>
DELETE
FROM USUARIO
WHERE DNI = 12345;

DELETE
FROM PRESTAMO
WHERE IdPrestamo = 1;

En una frase: SELECT recupera datos: eliges columnas (SELECT), tabla (FROM), filtro (WHERE) y orden (ORDER BY).

  • La sentencia SELECT se utiliza para recuperar datos de la base de datos.

FROM <tabla>
WHERE <condición>

Consultas en múltiples tablas: INNER JOIN

En una frase: INNER JOIN pega filas de dos tablas cuando cumplen una condición (normalmente, que la clave foránea de una coincida con la clave primaria de la otra).

  • Es habitual que los datos a consultar estén distribuidos en varias tablas relacionadas entre sí. Por ejemplo: título del libro en un préstamo; DNI usuario en un préstamo.
  • El operador INNER JOIN permite unir dos tablas indicando bajo qué criterio se deben emparejar las filas de una tabla con las de la otra:
    • Se forman todos los pares posibles de filas que cumplan el criterio.
  • Las filas de cualquiera de las dos tablas que no cumplan el criterio para ningún posible par no aparecerán entre los resultados.
  • Las filas de cualquiera de las dos tablas que cumplan el criterio para varios pares aparecerán varias veces entre los resultados, una por cada par.
SELECT *
FROM PRESTAMO
INNER JOIN USUARIO
ON PRESTAMO.IdUsuario = USUARIO.IdUsuario;

SELECT Nombre, Titulo, FechaPrestamo, FechaDevolución
FROM PRESTAMO
INNER JOIN USUARIO
ON PRESTAMO.IdUsuario = USUARIO.IdUsuario
INNER JOIN LIBRO
ON PRESTAMO.IdLibro = LIBRO.IdLibro
ORDER BY FechaPrestamo;
Resultado descrito La primera consulta devuelve las columnas de PRESTAMO seguidas de las de USUARIO, una fila por préstamo. La segunda encadena dos JOIN y devuelve, por ejemplo, «José González – Harry Potter y la cámara secreta – 2019-01-12 – 2019-01-27», ordenado por fecha de préstamo. Con LEFT JOIN (no visto en las diapositivas) sí aparecerían las filas sin pareja de la tabla izquierda, con NULL en las columnas de la derecha.

Garantías ACID en un sistema de base de datos

En una frase: una transacción es un grupo de operaciones que debe tratarse como una sola; ACID son las cuatro promesas que hace el gestor sobre ella.

ACID: acrónimo que describe cuatro garantías que un sistema de bases de datos debe cumplir al ejecutar una transacción.

  • Atomicidad (Atomicity): la transacción se completa entera o no se completa en absoluto. Si falla a mitad, se deshacen los cambios ya hechos.
  • Consistencia (Consistency): la transacción lleva la base de datos de un estado válido a otro estado válido, respetando las reglas definidas (claves, restricciones, tipos).
  • Aislamiento (Isolation): las transacciones concurrentes no interfieren entre sí; el resultado es el mismo que si se ejecutaran una tras otra.
  • Durabilidad (Durability): una vez confirmada, la transacción persiste aunque haya un fallo posterior, como un corte de luz.
Ejemplo Una transferencia de 100 € resta de una cuenta y suma en otra. Atomicidad: no puede quedar solo la resta. Consistencia: el saldo total se conserva. Aislamiento: otra consulta simultánea no ve el estado intermedio. Durabilidad: tras el «commit», un apagón no la deshace.

Introducción: tres escenarios que justifican un data warehouse

En una frase: un data warehouse (almacén de datos) es una base de datos aparte, pensada para analizar, a la que se copian datos de los sistemas del día a día.

Escenario 1

  • ACME S.A. es una compañía con presencia en Gran Canaria, Tenerife, Fuerteventura y Lanzarote. En cada isla existe una base de datos.
  • Problema: el responsable de ventas quiere conocer las ventas trimestrales (consulta de ventas por categoría y por sucursal para el primer trimestre).
  • Solución: obtener la información de ventas de cada una de las bases de datos y almacenarla en una base de datos en una única localización (el data warehouse), sobre la que trabajan las herramientas de análisis.

Escenario 2

  • Una empresa dispone de una gran base de datos operacional.
  • Problema: cada vez que se desea obtener algún informe, el sistema se ralentiza y los operadores deben esperar para introducir las operaciones.
  • Solución: extraer los datos necesarios de la base de datos operacional; almacenarlos en una base de datos intermedia; actualizar la base de datos intermedia a intervalos regulares para mantener la información actualizada.
Imagen descrita Antes: las operaciones y los informes de gestión atacan a la misma base de datos operacional, lo que provoca retrasos. Después: las operaciones (transacciones) siguen yendo a la base operacional; un proceso «extraer datos» copia periódicamente lo necesario al data warehouse, y los informes de gestión salen de ahí.

Escenario 3

  • Gofio Software es una pequeña empresa que empieza a tener cierta facturación. Sus responsables quieren que la compañía comience a crecer, para lo que necesitan información para tomar las decisiones correctas.
  • Solución: mejorar la calidad de los datos antes de cargarlos en el data warehouse; realizar limpieza y transformación de los datos antes de cargarlos; utilizar herramientas de análisis para generar consultas específicas.
Imagen descrita Data warehouse → herramienta de análisis → gráfico de ventas en el tiempo → el gerente decide entre «expansión» y «mejorar».

Necesidad de un data warehouse

  • Fuentes dispersas de datos: los datos por sí mismos no representan información.
    • Solo el 20% de los datos pueden ser utilizados en sistemas de decisión.
  • El análisis requiere del procesado de gran cantidad de datos.
    • Ralentización del sistema de transacciones, que está diseñado para el trabajo diario.
  • La arquitectura de un data warehouse es diferente de una base de datos operacional y permite realizar análisis más rápidamente.

Diapositiva 15

Definición de data warehouse (Bill Inmon)

«Un data warehouse es un almacén de datos temático, integrado, histórico y no volátil que es usado básicamente en un entorno de decisión empresarial.» — Bill Inmon, Building the Data Warehouse, 1996.

  • Temático: organizado en torno a los temas principales de la empresa más que a las áreas principales de aplicación. Se necesita almacenar datos que ayuden a la toma de decisiones más que datos orientados a aplicaciones.
  • Integrado: datos procedentes de diferentes aplicaciones en la empresa. Pueden existir inconsistencias, por lo que se deben eliminar para presentar una visión unificada a los usuarios (proceso de integración y transformación, ETL).
  • Histórico: los datos siempre se añaden, por lo que se tiene la evolución de los mismos a lo largo del tiempo → la componente temporal está implícita. Sistema operacional → presente; data warehouse → histórico de los datos.
  • No volátil: los datos siempre se añaden y no se producen modificaciones. Incorporación continua de nuevos datos, integrándolos con los ya existentes.
Imágenes descritas «Integrado»: varias aplicaciones operativas (engranajes) y áreas de negocio vuelcan sus datos en un único data warehouse del que sale conocimiento (bombilla). «No volátil»: en el sistema operacional los datos se insertan, modifican y borran; en el data warehouse solo se cargan y se consultan.

Diapositivas 17–21

Modelo dimensional: hechos y dimensiones

En una frase: el modelo dimensional separa lo que se mide (hechos: importes, cantidades) de el contexto de la medida (dimensiones: quién, cuándo, dónde, qué).

  • ¿Cómo es posible realizar análisis usando grandes cantidades de datos? La clave reside en una arquitectura de la base de datos sencilla: el modelo dimensional.
  • El modelo dimensional se construye de forma que acelere la ejecución de consultas.
  • Los datos se dividen en dos categorías (dos tipos de tablas en la base de datos):
    • Hechos: representan datos medibles de un «evento del negocio».
    • Dimensiones: representan el contexto del «evento del negocio».
    • P. ej., cuando un cliente compra un paquete de gofio de 2 euros: este es el «evento del negocio». Quién, cuándo, dónde, … es el contexto del «evento».
  • Cuando se desarrolla el modelo dimensional se necesita comprender los procesos de la empresa para identificar los eventos y sus estados.

Diapositivas 27, 30, 32

Tablas de dimensiones

  • Las tablas de dimensiones representan el contexto del evento → circunstancias que rodean al evento.
  • Contienen gran cantidad de atributos (columnas) (hasta 100) y un número relativamente pequeño de registros (filas).
  • Es deseable que los atributos de las dimensiones sean textuales.
  • En muchos casos se podría decir que, dependiendo de lo bien definidos que estén los atributos de las tablas de dimensiones, así de bueno sería el data warehouse.
  • Cada dimensión describe una vista del negocio por medio de la cual realizar los análisis.
  • El tamaño de las dimensiones suele ser del 10% del tamaño del data warehouse.
  • Los atributos normalmente se representan de forma jerárquica como enlaces:
    • Año → trimestre → mes → semana → día
    • País → provincia → ciudad → tienda
    • Producto → tipo → marca

  • La medida se obtiene de la intersección de todas las dimensiones (p. ej. tiempo, producto, localización, …).

    • Facilita la creación de informes agrupando (sumar, contar) varios millones de registros → el informe se resume en una o dos páginas.

Diapositivas 34–36

Estructura (arquitecturas) de un data warehouse: una, dos o tres capas

En una frase: cuántos «pisos» de datos hay entre los sistemas operacionales (el día a día) y los sistemas informacionales (el análisis).

  • Single-layer: opera directamente sobre los datos operacionales; no se dispone de histórico; cada dato se almacena una sola vez; data warehouse virtual; volumen más reducido de datos.
  • Two-layer: tiempo real + datos derivados; separación del nivel de negocio (tiempo real) del nivel de análisis; es la estructura más utilizada actualmente en la industria.
  • Three-layer: la transformación de los datos de tiempo real en datos derivados necesita realizarse en dos pasos. Real-time data → reconciled data (implementación física del data warehouse) → derived data (nivel de vista: «necesidades de información concretas»).
Aclaración «Datos reconciliados» = datos ya integrados y limpios de todas las fuentes. «Datos derivados» = vistas resumidas para un uso concreto (p. ej. un data mart de ventas). En la versión single-layer, tanto los sistemas operacionales como los informacionales leen la misma capa de datos en tiempo real.

Diapositivas 38–40

Integración de datos: proceso ETL

En una frase: ETL = Extraer los datos de las fuentes, Transformarlos (limpiar, unificar) y cargarlos (Load) en el data warehouse.

  • Proceso ETL: E – Extracción; T – Transformación; L – Carga (Load).
  • Es el proceso más importante y más costoso: supone alrededor del 80% del tiempo necesario para construir un DW.
  • Dos fases: inicial (al comienzo de la construcción) e incremental (mensual, semanal o diario dependiendo de la naturaleza del negocio).

Dificultades del proceso ETL

  • Diversidad e incompatibilidad de las fuentes de datos:
    • Los datos provienen de sistemas implementados en diferentes entornos y sistemas operativos.
    • Muchos sistemas operacionales son propietarios y utilizan en algunos casos tecnologías obsoletas.
  • Los sistemas fuente no almacenan históricos sobre cambios en los datos → la calidad de los datos es dudosa en sistemas que han ido cambiando con el tiempo.
  • La naturaleza de los negocios es cambiante → la estructura de la fuente de datos cambia con el tiempo; el proceso ETL se debe ir adaptando con el tiempo.

Problemas con la integración de datos

  • Añadir los datos en el DW no es solo obtenerlos y transformarlos: los datos en las fuentes están «sucios» (dirty).
  • Algunos problemas: el mismo dato aparece con diferentes nombres; diferentes datos tienen el mismo nombre; algunos datos están localizados en un sitio específico y en ningún otro; diferentes claves para el mismo dato; …
  • La misma persona aparece escrita de diferentes maneras: Agarwal, Agrawal, Aggarwal.
  • El nombre de la compañía se escribe diferente: Persistent Systems, PSPL, Persistent Pvt. LTD.
  • Utilizar diferentes nombres para la misma cosa: vehículo, coche, automóvil, …
  • Campos vacíos; valores incorrectos (errores de escritura, …).

Diapositivas 41–46

Fases del ETL: extracción, validación y transformación

  • Fase de extracción, tareas: identificación de todos los datos necesarios en el DW; identificación de todas las fuentes de datos; definición de reglas para la obtención de los datos. Tipos de extracción: inicial e incremental.
  • Fase de validación: los datos se validan según un conjunto de restricciones. P. ej., un dato debe ser un entero y se recibe una cadena de caracteres → puede indicar que la fuente de datos está corrupta. Fase de filtrado para asegurar que los datos correctos siguen el flujo.
  • Fase de transformación: normalmente los datos deben ser transformados antes de ser almacenados en el DW. Establecer las transformaciones a realizar y las reglas de limpieza de los datos. Mejorar la calidad de los datos → parte más compleja de la transformación.
Ejemplos de transformación unificar formatos de fecha, pasar «H/M» y «Hombre/Mujer» a un mismo código, convertir monedas, quitar duplicados del tipo Agarwal/Agrawal, calcular columnas derivadas (precio total = cantidad × precio unitario).

Diapositivas 46–47

Fase de carga (load)

  • Cargar los datos en el DW. Tres tipos diferentes de carga:
    • Carga inicial → se carga el DW completo.
    • Carga incremental → carga periódica con los cambios diarios de los datos.
    • Refresco completo → algunas tablas del DW se borran y se recargan nuevamente con datos.
  • Carga incremental de las tablas de dimensiones:
    • Necesidad de almacenar la fecha de última modificación en las tablas origen.
    • Cargar todos los registros de las tablas origen con modificación posterior a la última actualización.
    • Comparar cada registro recuperado con los existentes en la tabla de dimensión correspondiente para detectar si es una nueva entrada o modificación de una existente.
  • Carga incremental de las tablas de hechos:
    • Proceso más sencillo que la carga incremental de dimensiones → no hay que comparar los registros cargados con los existentes.
    • Necesidad de almacenar la última carga correcta.
    • Seleccionar todos los registros de las tablas origen más recientes que la última carga correcta.
Por qué los hechos son más fáciles Un hecho (una venta) nunca cambia una vez ocurrido: solo se añaden ventas nuevas. Una dimensión (un cliente) sí puede cambiar (se muda), así que hay que decidir si es nuevo o una actualización.

Diapositiva 51

Data lake

En una frase: un data lake es un gran depósito central donde se guarda todo tal cual llega (tablas, logs, imágenes, JSON…), sin darle estructura hasta el momento de analizarlo.

  • Objetivo del data warehouse: inteligencia y analítica de negocio.
  • Las empresas tienen otras fuentes de información además de las operacionales internas: archivos de log; datos de flujos de interacción (click-streams); redes sociales; dispositivos conectados a la red (IoT).
  • Para incluirlas en un data warehouse → procesar y estructurar como modelo relacional.
  • Data lake: almacén de datos centralizado con datos estructurados (similar al data warehouse) y datos no estructurados.
    • Los datos se almacenan tal y como se obtienen (en crudo) sin preprocesamiento.
    • Fuente de información para herramientas de análisis de datos.
    • Pueden coexistir data warehouse y data lake.

Organización de un data lake

  • Estructura de almacenamiento plana.
  • Identificador único por cada elemento → existencia de metadatos.
  • No existe selección de los datos: se almacenan todos los datos, los que se utilizan actualmente, los que se pueden utilizar y datos que nunca van a ser utilizados (se incorporan solo porque podrían ser utilizados algún día).
  • Bajo coste de ampliación de un data lake.

Arquitectura de un data lake

  • Inicialmente construidos usando Apache Hadoop Distributed File System (HDFS).
  • Actualmente, almacenamiento de objetos en la nube: Amazon Simple Storage Service (S3), Microsoft Azure Blob Storage o IBM Cloud Object Storage.
  • Almacenamiento de datos separado de recursos de computación → incrementar el almacenamiento sin afectar a los recursos computacionales.

Diapositivas 52–61

Data lakehouse y arquitectura medallón

En una frase: un lakehouse guarda los datos baratos y en crudo como un lake, pero añade encima una capa de tablas con transacciones y esquema para consultarlos con la fiabilidad de un warehouse.

  • Combina las características de un data lake y un data warehouse en una única solución de gestión de datos.
    • Característica del data lake: almacenar datos en cualquier formato (estructurado, semiestructurado o no estructurado) a bajo coste.
    • Característica del data warehouse: soporta consultas rápidas y tareas analíticas optimizadas.

¿Qué intenta resolver?

  • Data lake: almacenamiento barato y flexible, pero sin transacciones ACID ni control de esquema; riesgo de data swamp (pantano de datos).
  • Data warehouse: calidad y rendimiento para BI, pero caro, rígido y poco apto para datos no estructurados.
  • Resultado: copias de datos entre ambos sistemas, duplicidad, latencia y costes.

¿Cómo funciona?

  • Almacena los datos en el lago (almacenamiento de objetos barato, en formatos abiertos).
  • Añade una capa de tablas transaccionales encima del data lake:
    • Transacciones ACID sobre archivos, para que lecturas y escrituras concurrentes sean consistentes.
    • Aplicación y evolución de esquema, para rechazar datos malformados y gestionar cambios de columnas.
    • Consultar versiones anteriores de una tabla.
    • Acceso compartido para ingeniería de datos, BI y machine learning sobre los mismos datos.

Arquitectura medallón (Medallion) → propuesta por Databricks

  • Nivel bronce: datos en crudo incorporados con ninguna o mínima transformación.
  • Nivel plata: tareas de limpieza, validación y unificación de fuentes.
  • Nivel oro: nivel de negocio con datos agregados, refinados y preparados para tareas de BI y aprendizaje automático.
  • Similar a la estructura de tres niveles de un data warehouse: operacionales → reconciliados → derivados.

Diapositivas 24–29

Indicadores clave de rendimiento (KPI)

En una frase: un KPI es uno de los pocos números que de verdad dicen si la organización va bien hacia sus objetivos, y se mira continuamente.

  • Key Performance Indicators (KPIs) son un tipo especial de indicador.
  • Representan un conjunto de medidas que se centran en aquellos aspectos de rendimiento de la organización que son más críticos para el éxito actual y futuro de la organización.
  • Los KPI se muestran normalmente en los scorecards → valor actual y valor objetivo. (David Parmenter, 2010, Key Performance Indicators, John Wiley & Sons.)

Por qué los gestores necesitan KPI

  • Seguimiento sin esperar informes: un equipo que avanza poco hacia su objetivo se detecta a tiempo.
  • Responsabilidad clara: cada miembro ve las cifras ligadas a su trabajo.
  • Decisiones más rápidas: los datos en tiempo real reflejan la situación actual.
  • Detección temprana: las tendencias muestran problemas antes de que se agraven.

Características de los KPI

  • No son medidas financieras: una medida expresada en términos monetarios es el resultado de muchos factores que deberían ser analizados.
  • Medirse frecuentemente: deben obtenerse 24/7, ya que no se trata de medir cómo era la organización en el pasado sino cómo es en el presente. De lo contrario se tomarían medidas inútiles.
  • Tener interés para los gestores: un KPI debe seguirse constantemente, por lo que debe tener interés para los gestores.
  • Deben ser entendidos por el personal: cada indicador debe estar asociado claramente a una acción a seguir.
  • Estar ligados a responsables: un KPI debe estar asociado a un responsable, de forma que se pueda pedir información de por qué evoluciona de una determinada manera.
  • Tener un efecto importante en la organización: al estar ligados a objetivos cruciales de la organización.
  • Tener un efecto positivo en otros indicadores: la mejora en un KPI debe llevar asociada la mejora en alguna otra medida del negocio.

Cómo gestionar los KPI en la práctica

  • Comunicar con claridad qué se mide, por qué importa y qué resultado es bueno.
  • Automatizar el seguimiento para dedicar el tiempo a interpretar los datos.
  • Fijar objetivos alcanzables: los objetivos inalcanzables generan desmotivación.
  • Integrar la responsabilidad en la rutina con revisiones periódicas y reconocimiento.
  • Revisar los KPI cuando cambie la estrategia.
  • Conectar datos entre áreas para que marketing, ventas y finanzas usen las mismas cifras.

Cubo de datos

En una frase: un cubo de datos organiza un número (p. ej. ventas) según varias dimensiones a la vez (tiempo, producto, ciudad…); cada celda es la venta de un producto, en un trimestre, en una ciudad.

Cuboides: base, cúspide y grafo (lattice)

En una frase: un cuboide es el cubo que resulta de agrupar por un subconjunto de las dimensiones; con n dimensiones hay 2ⁿ cuboides, desde «todo detallado» hasta «un único total».

  • Los diferentes niveles de resumen dan lugar a diferentes cubos → cuboide.
  • Dado un conjunto de dimensiones → se puede generar un cuboide para cada posible subconjunto.
  • El conjunto de todos los cuboides forma un grafo donde cada uno representa los datos a un nivel de resumen o group-by.
  • Cuboide que representa el menor grado de resumen (no existe ninguna agrupación) → cuboide base.
  • Cuboide con el mayor grado de resumen (agrupación completa) → cuboide cúspide (apex).
  • Resto de cuboides → cuboides no base.
  • El cuboide cúspide para el ejemplo sería el total de ventas.
Relación con SQL Cada cuboide equivale a una consulta GROUP BY: el cuboide (tiempo, ciudad) es SELECT tiempo, ciudad, SUM(ventas) … GROUP BY tiempo, ciudad; la cúspide es SELECT SUM(ventas) sin agrupar.

Jerarquía de conceptos

En una frase: los niveles de detalle de una dimensión, de lo más concreto a lo más general (calle → ciudad → provincia → país).

  • Define una secuencia de transformaciones de conceptos de bajo nivel a conceptos de más alto nivel. Ejemplo para la dimensión localización: ciudad → provincia → país.
  • Muchas jerarquías de conceptos vienen implícitas en el diseño de la base de datos. La dimensión localización se define por los campos calle, ciudad, provincia y país.
    • Los campos están relacionados mediante una relación de orden total → jerarquía de conceptos.
  • En otras dimensiones los campos definen una relación de orden parcial, formando un grafo.
  • La jerarquía de conceptos se puede obtener mediante el agrupamiento o discretización de un campo o dimensión → jerarquía set-grouping.
  • Ejemplo de jerarquía set-grouping para el precio: ($0…$1000] se divide en ($0…$200], ($200…$400], ($400…$600], ($600…$800], ($800…$1000], y cada uno en tramos de 100 $: ($0…$100], ($100…$200], …, ($900…$1000].

Medidas: distributivas, algebraicas y holísticas

En una frase: una medida es la función numérica (suma, media, mediana…) que se calcula en cada celda; se clasifica según si se puede calcular por trozos y combinar después.

  • Un dato en un cubo se corresponde con la intersección de pares dimensión-valor. P. ej.: {tiempo = primer trimestre, localización = Vancouver, tipo = ordenador} → 825.
  • Medidas del cubo de datos → función numérica que se puede evaluar para cada dato del cubo. Se calcula agregando los datos correspondientes a las dimensiones.
  • Las medidas se pueden agrupar en tres categorías según el tipo de función de agregación utilizada:
TipoDefinición (diapositivas)Ejemplos
DistributivasSe pueden calcular de forma distribuida: se dividen los datos en n conjuntos y se aplica la función de agregación a cada conjunto. Si el resultado de aplicar la función a los n resultados intermedios es igual a aplicar la función a todos los datos → medida distributiva.suma(), min(), max(), count()
AlgebraicasSe deben poder calcular mediante una función algebraica dependiente de M parámetros, cada uno de los cuales se obtiene mediante una función de agregación distributiva.promedio() = suma()/count(); stddev(); min_N() y max_N()
HolísticasSon aquellas para las que no existe una medida algebraica que las calcule.mediana(), moda()
Ejemplo para entenderlo Datos {1, 2, 3} y {10, 20}. Suma (distributiva): 6 + 30 = 36, igual que sumar todo. Media (algebraica): no vale promediar las medias (2 y 15 → 8,5); hay que guardar suma y count de cada trozo (6,3) y (30,2) → 36/5 = 7,2. Mediana (holística): con las medianas parciales (2 y 15) no se puede obtener la mediana global (3); hace falta ver todos los datos. Por eso las holísticas son las más caras de precalcular en un cubo.

Lenguaje de consulta MDX (MultiDimensional eXpressions)

En una frase: MDX es el «SQL de los cubos»: en vez de filas y columnas de una tabla, pides qué miembros de cada dimensión van en cada eje del resultado.

-- comentario
SELECT {set 0} ON COLUMNS,   /* comentario */
       {set 1} ON ROWS,      // comentario
       {set n} ON AXIS(n)
FROM [cube]
WHERE (tuple)
  • Los ejes hacen referencia a las «dimensiones» del cubo resultante.
  • JPivot no puede mostrar resultados con más de dos dimensiones (COLUMNS, ROWS).
  • MDX no es SQL:
    • «Cube in, cube out» en MDX.
    • Después de la cláusula SELECT debe ir un conjunto (set).
    • La cláusula FROM solo admite un único cubo.
    • La cláusula WHERE incluye los ejes slicers.
  • Cada conjunto devuelve elementos (miembros) de una determinada dimensión obtenidos mediante una expresión multidimensional.
  • Expresiones multidimensionales:
    • [nivel 1].[nivel 2] … .[miembro]
    • [nivel 1].[nivel 2] … .MEMBERS
    • [nivel 1].[nivel 2] … .CHILDREN
    • [nivel 1].[nivel 2] … .[miembro1]:[miembro2]
    • DESCENDANTS([nivel 1].[nivel 2] …, [nivel])
  • Conjunto (set): {expr. multidim. 1, expr. multidim. 2, …}
ExpresiónConjunto de miembros que devuelve
[Product].[Product Family].[Skinner]el miembro Skinner
[Product].[Product Name].MEMBERS{Portsmouth, Skinner, Washington, Johnson, Toby}
[Product].[Drink].CHILDREN{Portsmouth, Skinner, Washington}
[Product].[Drink].[Skinner]:[Washington]{Skinner, Washington}
DESCENDANTS([Product].[Food], [Product Name]){Johnson, Toby}

Ejemplos de consultas

SELECT {[Time].[Year].[1997], [Time].[Year].[1998]} ON COLUMNS,
       {[Store].[Store Name].MEMBERS} ON ROWS
FROM [Sales]
WHERE ([Measures].[Store Sales])

Resultado: tabla con columnas 1997 y 1998 y una fila por tienda (HQ, Store 6, Store 7, …) con las ventas de cada tienda.

SELECT {[Time].[Year].[1997].CHILDREN} ON COLUMNS,
       {[Store].[Store City].MEMBERS} ON ROWS
FROM [Sales]
WHERE ([Measures].[Store Sales])

Resultado: columnas Q1, Q2, Q3, Q4 (los hijos de 1997) y una fila por ciudad.

SELECT {[Time].[Year].[1997].CHILDREN} ON COLUMNS,
   FILTER(
     {[Store].[Store City].MEMBERS},

   ) ON ROWS
FROM [Sales]
WHERE ([Measures].[Store Sales])

SELECT Measures.MEMBERS ON COLUMNS,
   ORDER(
     [Store].[Store City].MEMBERS,
     Measures.[Sales Count], BDESC
   ) ON ROWS
FROM [Sales]

   HEAD( ORDER( {[Store].[Store City].MEMBERS},
                Measures.[Sales Count], BDESC

   ) ON ROWS
FROM [Sales]

   ) ON ROWS
FROM [Sales]
WHERE (Measures.[Profit])

SELECT [Time].[1997].CHILDREN ON COLUMNS,
   NON EMPTY(

   ) ON ROWS
FROM [Sales]

¿Qué es CRM?

En una frase: CRM (Customer Relationship Management) es la estrategia para conocer a cada cliente y tratarlo de forma personalizada, de modo que se quede y aporte más.

Reglas de asociación: definiciones

En una frase: una regla de asociación es un «si aparece esto, suele aparecer también aquello», descubierto contando cuántas transacciones lo cumplen.

  • Se utilizan para descubrir elementos que aparecen asociados con frecuencia en un conjunto de datos.
  • Se asume que los atributos son nominales.
  • Inicialmente se desarrolló para el análisis de las cestas de la compra → encontrar si existe relación entre los productos comprados por los clientes.
    • Base de datos → conjunto de transacciones (cestas de la compra).
    • Transacción → conjunto de elementos elegidos por un cliente en una compra.
  • Aplicación → hábitos de compra, relación de páginas visitadas, documentos relacionados, etc.
  • Responder a preguntas del tipo: si un cliente compra el producto A, ¿qué probabilidad hay de que también compre el producto B? ¿Qué otros productos compra un cliente si compra los productos C y D? ¿Qué páginas web suelen visitar los usuarios de un sitio web?
  • Ejemplo de regla de asociación: si pan y mantequilla entonces leche (confianza 90%).

Notación formal

  • I = {I1, I2, …, In} un conjunto de elementos.
  • T = {t} un conjunto de transacciones. Cada transacción t se representa como un subconjunto de I.

Algoritmo Apriori

En una frase: Apriori busca los conjuntos frecuentes de tamaño 1, luego de tamaño 2 combinando solo los frecuentes, y así sucesivamente, porque un conjunto nunca puede ser más frecuente que sus partes.

  • Buscar todos los itemsets más frecuentes → tienen un soporte superior a un mínimo.
  • Extender los itemsets más frecuentes de forma «bottom up» → se añade un elemento cada vez (generación de candidatos) y se comprueban con los datos.
  • Se basa en la propiedad Apriori: cualquier superconjunto de un itemset infrecuente también es un itemset infrecuente.
  • El algoritmo termina cuando no se pueden realizar más extensiones.

Pasos

  1. Buscar todos los itemsets que tienen un soporte por encima de un soporte mínimo (minsup).
  2. Con los itemsets encontrados, generar las reglas de asociación manteniendo solo las que superan una confianza mínima (minconf):
    1. Para cada itemset X, encontrar todos los subconjuntos.
    2. Para cada subconjunto {X, Ik}, generar la regla X ⇒ Ik si minconf ≤ soporte({X, Ik}) / soporte({X}).
    3. Si una regla no supera la confianza mínima, ningún subconjunto de la misma la supera → no considerarlas.

Diapositiva 41

Sistemas de recomendación

En una frase: un sistema de recomendación filtra el catálogo para enseñar a cada usuario lo que probablemente le interese, a partir de lo que hizo antes él o gente parecida.

  • Recomendación a un cliente en función de intereses → mejor experiencia de usuario.
  • Esquema de filtrado de productos/servicios más relevantes para cada cliente/usuario: obtener el comportamiento del usuario en el pasado y recomendar productos en base a ese comportamiento.
  • Aproximaciones:
    • Recomendar los productos más populares entre todos los usuarios → solución para nuevos usuarios. Inconveniente: las mismas recomendaciones para todos los usuarios.
    • Segmentar usuarios por preferencias → recomendar productos en función del segmento. Inconveniente: complejidad creciente en función del número de usuarios.
  • Recopilación de datos históricos de usuarios: paso más importante → de la calidad y cantidad de los datos recopilados depende la calidad de la recomendación.
    • Explícita: el usuario indica valoración, opinión, etc.
    • Implícita: historial de búsqueda, tiempo de visualización, compras, pedidos, etc.

Filtrado basado en contenido

  • Filtrado de información relevante para realizar la recomendación.
  • Recomendar productos similares a los que le han gustado en el pasado al usuario.
  • Almacenar comportamiento pasado: vector de perfil. Información asociada a productos: vector del elemento.
  • Similitud: distancia coseno entre ambos vectores. Proceso de búsqueda: consulta el vector de perfil de usuario y los productos como documentos a emparejar.
  • Inconveniente: recomienda productos del mismo tipo; no va a recomendar productos diferentes a los vistos en el pasado.

Problemas de los sistemas de recomendación

  • Matrices escasas: los usuarios no acceden a todos los productos, lo que da lugar a vectores escasos (llenos de huecos).
  • Arranque en frío:
    • Nuevo usuario: no existe historial del usuario en cuanto a preferencias. Solución: recomendar productos más similares.
    • Nuevo producto: se añade un nuevo producto al sistema. Solución: recomendación basada en contenido.

Áreas de aplicación del NLP

  1. Search and Information Retrieval (IR) → almacenamiento y recuperación de documentos, incluyendo motores de búsqueda y búsquedas por palabras clave.
  2. Document Clustering → agrupamiento y categorización de términos, párrafos o documentos utilizando métodos de agrupamiento de aprendizaje automático.

Diapositivas 9–10

Preprocesado – normalización

En una frase: limpiar y homogeneizar el texto para que la misma idea se escriba siempre igual antes de contar palabras.

  • Una de las tareas en el procesamiento de lenguaje natural es convertir un texto no estructurado en información numérica estructurada → preprocesado de los documentos:
  1. Seleccionar el ámbito (documento, párrafo, …).
  2. Separar en palabras (tokens).
  3. Eliminar stopwords.
  4. Stemming/lemmatization → normalizar palabras.
  5. Corregir errores ortográficos.
  6. Detectar los finales de frases.
  7. Normalizar minúsculas/mayúsculas.

Seleccionar el ámbito del documento

  • Dependiente de la aplicación. Clasificación de spam → e-mail completo.
  • Documentos grandes → necesidad de considerar todo el documento o partes del mismo: clasificación o clustering de documentos → documento completo; análisis de opiniones o recuperación de información → párrafos o secciones.

Diapositivas 12–13

Separación por palabras (tokenización)

En una frase: partir el texto en unidades (tokens), normalmente palabras.

  • Mayoría de lenguajes → utilizar espacios y signos de puntuación. Estrategia simple y sencilla de implementar.
  • Manejo de acrónimos y abreviaciones → la estrategia anterior puede dar resultados incoherentes. P. ej. EE.UU. se separa en EE UU cuando debería ser EEUU.
  • Separación inteligente → detecta los acrónimos y abreviaciones y no los separa.
  • Dependiendo de la aplicación, los signos de puntuación pueden ser un elemento importante. P. ej.:
    • ¿Puedo entrar? No, espere / ¿Puedo entrar? No espere
    • No queremos saber / No, queremos saber
    • ¿Le expulso? ¡No tenga clemencia! / ¿Le expulso? ¡No, tenga clemencia!

Diapositivas 14–15

Eliminación de stopwords (stopping)

En una frase: quitar las palabras muy frecuentes que casi no aportan significado (artículos, preposiciones, pronombres).

  • En muchas tareas de procesamiento de lenguaje natural es aconsejable eliminar palabras como los artículos, pronombres, conectores, etc.
  • El rendimiento de la gran mayoría de las aplicaciones de NLP no se ve afectado.
    • Excepciones: recuperación de la información → las frases pueden perder el significado original si se eliminan las stopwords.
  • Algunas stopwords del inglés: a, about, an, are, as, at, be, by, for, from, how, in, is, of, on, or, that, the, these, this, to, was, what, when, where, who, will, with.
  • Caso especial – encabezados de correos: el encabezado de los correos (to:, from, subject) puede sesgar los resultados de algunas aplicaciones. Ejemplo de la diapositiva: líneas Return-path, Delivery-date, X-ClientAddr, Received, Message-ID, From, Date, Subject, MIME-Version, Content-Type.
  • Caso especial – boilerplate: los avisos legales al pie de los correos pueden ser mucho mayores que el texto del correo → enmascarar el significado del correo (ejemplo: el típico «This email and any files transmitted with it are confidential…»).

Diapositivas 16–18

Stemming y lematización (algoritmo de Porter)

En una frase: reducir las variantes de una palabra (cats, cat; running, run) a una forma común para contarlas juntas.

  • Proceso de transformar las palabras a una forma normal.
    • Stemming: eliminación de sufijos → el resultado puede no pertenecer al idioma.
    • Lemmatization: obtener raíz (lema) → el resultado pertenece al idioma.
  • Obtener la palabra raíz a partir de diferentes variaciones sintácticas: eliminación de sufijos y prefijos; convertir a singular; pasar verbos a infinitivo.
  • En inglés el algoritmo de stemming más popular es el propuesto por Porter y su versión Porter2 (snowball). M. F. Porter, «An Algorithm for Suffix Stripping», Program, 14(3), pp. 130-137, 1980.
  • Algoritmo de Porter: método basado en reglas → utilización de heurística; se basa en la eliminación de sufijos; consiste en conjuntos de reglas que se aplican en orden. Ejemplo de regla: ATIONAL → ATE (relational → relate).
  • Reglas: eliminar plurales; eliminar terminaciones de pasado y gerundio (-ed, -ing); sustituir «y» finales por «i»; eliminar sufijos comunes como -al, -ance, -ence, -able, -ible, etc.; eliminar «e» final si va precedida de consonante; eliminación de dobles consonantes al final.

Stemmingthe cat are friendli animdata scienc student program realli well and they are veri enthusiast

El stemming es más rápido; la lematización necesita diccionario y, a veces, saber la categoría gramatical (por eso deja «animals» si no sabe que es un sustantivo).

Diapositivas 19–22

Corrección ortográfica, emojis, detección de frases y mayúsculas

Corrección ortográfica

  • La corrección ortográfica es importante → la misma palabra escrita de dos formas diferentes da lugar a dos entradas diferentes.
  • Aproximaciones: basada en diccionario (se corrigen los errores más habituales); similitud según distancia de edición o pronunciación.
  • Dependiendo de las fuentes puede ser necesario o no: textos literarios o periodísticos → no necesaria; textos de la red → muy importante.
Distancia de edición (Levenshtein): nº mínimo de inserciones, borrados o sustituciones de letras para pasar de una palabra a otra. «casa» → «cosa» = 1.

Tratamiento de emoji y emoticon

  • Diferencia: emoji → pequeña imagen para expresar una emoción o idea; emoticon → representación de una expresión facial utilizando caracteres y signos de puntuación, p. ej. :)
  • Tratamiento: considerarlos stopwords y eliminarlos, o convertirlos a palabras usando un diccionario (p. ej. «:)» → «feliz»). Guibon et al. (2016), From Emojis to Sentiment Analysis, WACAI 2016.

Detección de frases

  • Dividir el texto en frases completas.
  • Utilización de signos de puntuación como técnica más sencilla: tener en cuenta los puntos de las abreviaciones; los signos de puntuación dentro de texto entrecomillado no son final de frase.

Normalizar mayúsculas/minúsculas

  • Los textos incluyen mayúsculas para identificar comienzos de frase o nombres propios.
  • En algunas aplicaciones no es necesario: la mayúscula al comienzo de frase es innecesaria por la división en frases del texto; los nombres propios tienen diferente valor que otros elementos.
  • Normalizar a minúsculas (mayúsculas) todo el texto.

Diapositivas 23–28

Representación: bolsa de palabras y modelo de espacio vectorial

En una frase: cada documento se convierte en un vector con una posición por palabra del vocabulario; el orden de las palabras se olvida («bolsa»).

  • Objetivo → convertir un texto no estructurado en una estructura numérica.
  • Resultado → vector de características válido para ser utilizado por los algoritmos de modelado (clasificación, clustering, …).
  • La aproximación más utilizada es el concepto de «bag of words»: la secuencia en la que aparecen las palabras y las posiciones que ocupan en el documento no se tienen en cuenta.
  • El concepto de «bag of words» da lugar al denominado modelo de espacio vectorial, que tiene como características: puede aplicarse a diferentes formatos de documentos; puede manejar diferentes tipos de datos multimedia; la consulta, búsqueda, recuperación y ordenación de documentos se puede automatizar completamente; la mayor parte de la carga computacional se realiza durante el preproceso.

Diapositivas 30–32

Modelo booleano, modelo ponderado (TF) y ley de Zipf

Modelo booleano

Representación más sencilla: los pesos del vector son valores 0 o 1.

wij = 1 si el término ti aparece en el documento dj;   wij = 0 si no aparece

Modelo ponderado: Term Frequency (TF)

  • Es una extensión del modelo booleano: cada elemento del vector se corresponde con la frecuencia del término i en el documento j.
  • Normalizar el vector dividiendo cada término por la frecuencia de mayor aparición en el documento.
wij = tfi,j     normalizado:   wij = tfi,jmax{tf1,j, tf2,j, …, tf|V|,j}
tfi,j
nº de veces que aparece el término i en el documento j.
max{…}
la frecuencia de la palabra más repetida de ese documento. Al dividir, el término más frecuente vale 1 y el resto, entre 0 y 1; así un documento largo no tiene pesos mayores solo por ser largo.
Ejemplo En un documento donde «data» aparece 6 veces (la palabra más repetida) y «model» 3 veces: w(data) = 6/6 = 1; w(model) = 3/6 = 0,5.

Ley de Zipf

  • Un pequeño número de palabras aparece muchas veces en los textos.
  • Esas palabras con alta frecuencia de aparición son normalmente artículos, preposiciones, etc.
  • La mayor parte de las palabras aparecen pocas veces.
Imagen descrita Barras horizontales de frecuencia de palabras en un corpus: «the», «of», «and», «in», «to» con frecuencias de 150.000–260.000, y una larga cola de palabras (patients, cells, treatment, expression…) con frecuencias mucho menores. Formalmente, la frecuencia de la palabra en el puesto r es aproximadamente proporcional a 1/r.

Diapositivas 33–35

Modelo TF-IDF

En una frase: una palabra pesa mucho en un documento si aparece mucho en él (TF) y poco en los demás (IDF).

  • Es el modelo más utilizado para representar documentos.
  • Además de la frecuencia de los términos (TF) también incorpora la frecuencia inversa de documentos (IDF).
wij = tfi,j · idfi  si tfi,j ≥ 1;   wij = 0  si tfi,j = 0     siendo   idfi = log nni
tfi,j
frecuencia del término i en el documento j (o su versión normalizada).
n
número total de documentos de la colección.
ni
número de documentos en los que aparece el término i (al menos una vez).
n / ni
≥ 1; vale 1 si el término está en todos los documentos.
idfi
«inverse document frequency»: grande para términos raros, 0 para términos presentes en todos los documentos. La base del logaritmo no se fija en las diapositivas (en la práctica, natural o base 10; solo cambia la escala).
  • Comportamiento:
    • Un término i que aparece muchas veces en un documento j → tfi,j es alto.
    • Un término i que aparece en la mayoría de los documentos (ni → n) no es representativo → idfi = log(n/ni) → 0, es decir, se penaliza el peso de dicho término.
    • P. ej., el artículo «el» aparece muchas veces en los documentos, pero como aparece en la mayoría de los documentos no aporta mucho.
Ejemplo numérico Con n = 10 documentos: un término que está en 9 tiene idf = ln(10/9) ≈ 0,11; uno que está en 4 tiene idf = ln(10/4) ≈ 0,92. Aunque el primero aparezca 30 veces en un documento (tf·idf ≈ 3,2), uno raro que aparezca 5 veces pesa más (≈ 4,6).

N-gramas

  • Considerar como términos una secuencia de varias palabras: 2-grama (secuencia de dos palabras), 3-grama (tres), n-grama (n palabras).

Diapositivas 38–44

Matriz término-documento (TD)

Latent Semantic Analysis (LSA)

En una frase: LSA comprime la matriz término-documento con SVD para pasar de «palabras» a unos pocos «temas latentes», de modo que sinónimos quedan cerca aunque no compartan palabras.

Problemas de las matrices TD basadas en el espacio vectorial:

  • Sinónimos → diferentes palabras se refieren al mismo objeto (p. ej. coche y automóvil). Dan lugar a un valor de recall bajo.
  • Polisemia → la misma palabra tiene diferentes significados (p. ej. «banco» de sentarse, «banco» entidad financiera). Da lugar a un valor bajo de precision.
  • Posible solución: utilización de un diccionario de sinónimos.
  • LSA → intentar extraer la estructura semántica intrínseca contenida en los documentos mediante una transformación del espacio original en uno nuevo: términos con significados similares se mapean próximos entre sí; términos con significados diferentes se mapean distantes entre sí. (Deerwester, Dumais, Landauer, Furnas y Harshman, 1990, «Indexing by latent semantic analysis», Journal of the Society for Information Science, 41(6), 391-407.)
Recall y precision Recall = de los documentos relevantes, cuántos encuentras (si buscas «coche» y no aparecen los que dicen «automóvil», baja). Precision = de los que encuentras, cuántos son relevantes (si buscas «banco» financiero y salen parques, baja). En las diapositivas aparece a veces «Latent Search Analysis»: es una errata de Latent Semantic Analysis.

  1. Una consulta q compuesta por una serie de palabras y un conjunto de documentos di.
  2. Obtener la representación LSA de los documentos y los términos.

En una frase: en vez de diseñar a mano las características, una red neuronal lee el texto palabra a palabra y aprende la representación; una RNN tiene «memoria» de lo leído antes.

  • La aproximación de espacio vectorial a partir de BoW no tiene en cuenta la estructura de los documentos.
  • La estructura (secuencia) de las palabras es importante en determinadas aplicaciones de NLP.
  • Las redes neuronales recurrentes pueden utilizar información temporal para transformar secuencias de entrada en otras secuencias de salida.

Diapositivas 81–84

Long Short-Term Memory (LSTM)

En una frase: una LSTM es una RNN con una «cinta» de memoria (el estado de la celda) y tres puertas que deciden qué olvidar, qué escribir y qué leer en ella.

  • Arquitectura de red neuronal recurrente con celda de memoria basada en puertas (gated cell) que resuelve el problema del vanishing gradient.
  • Las puertas (gates) permiten a la red añadir o eliminar información al estado de la celda. Se componen de una capa sigmoide y una operación de multiplicación elemento a elemento.
  • El bloque LSTM posee tres puertas para controlar su funcionamiento. Cada bloque está compuesto de: puerta de olvido (forget gate), puerta de entrada (input gate), puerta de salida (output gate) y estado de la celda (Ct).
  • Estado de la celda Ct: se puede ver como un flujo de información que transporta información entre los bloques LSTM; se ve modificado por algunas operaciones lineales; se añade o elimina información mediante las puertas; fácilmente puede transportar la información sin cambios.

Diapositivas 85–92

Word embedding

En una frase: representar cada palabra como un vector denso de números reales (p. ej. 300 valores) de forma que palabras de significado parecido queden cerca.

  • Representación de una palabra como un vector de números reales.
  • Cualquier conjunto de valores puede ser una representación (word embedding) válida.
  • Una buena representación debería capturar la semántica de la palabra, la relación entre palabras y el contexto de diferentes palabras.
Diferencia con one-hot / BoW En one-hot cada palabra es un vector de |V| posiciones con un único 1: todas las palabras están a la misma distancia («rey» igual de lejos de «reina» que de «tenedor»). En un embedding, «rey» y «reina» quedan cerca, y es famoso que vec(rey) − vec(hombre) + vec(mujer) ≈ vec(reina).

BERT (Bidirectional Encoder Representations from Transformers)

En una frase: BERT es un modelo de lenguaje basado en el encoder del Transformer que lee la frase entera a la vez (en ambas direcciones), por lo que el vector de cada palabra depende de su contexto.

  • Desarrollado en 2018 por Google.
  • Entrenado con la Wikipedia (~2,5·10⁹ palabras) y el BookCorpus (~800·10⁶ palabras).
  • Modelo entrenado para dos tareas:
    • Determinar la palabra faltante: «Friend: "Dang! I'm out fishing and a huge trout just [blank] my line!"»
    • Predecir la siguiente frase: «Paul went shopping. He bought a new shirt.» (par correcto); «Ramona made coffee. Vanilla ice cream cones for sale.» (par incorrecto).
  • Variantes:
    • RoBERTa (Robustly Optimized BERT Approach): se entrenó con un conjunto de datos 10 veces mayor.
    • DistilBERT: variante más pequeña, rápida y ligera; 40% menor, conserva el 97% de sus capacidades de comprensión del lenguaje y es un 60% más rápida.
Imágenes descritas (1) Masked LM: la entrada «w1 w2 w3 [MASK] w5» pasa por un Transformer encoder; sobre cada salida Oi hay una capa de clasificación (fully-connected + GELU + Norm) y una capa embedding → vocabulario + softmax que predice la palabra oculta w′4.
(2) Arquitectura: «Transformer Model» con 12 bloques apilados (12x), cada uno con Multi-Head Attention y Feed Forward con «Add & Norm», más Input Embedding y Positional Encoding.
(3) Representación de la entrada: «[CLS] my dog is cute [SEP] he likes play ##ing [SEP]». Cada token suma tres embeddings: token embedding (la palabra o subpalabra), sentence/segment embedding (EA para la primera frase, EB para la segunda) y position embedding (E0 … E10). «##ing» indica que es continuación de la palabra anterior (WordPiece).
(4) Clasificación de una frase: «[CLS] Tok1 Tok2 … TokN» entra en BERT y la salida del token [CLS] (C) se usa como etiqueta de clase («Class Label»), p. ej. para análisis de sentimiento.
Bidireccional: a diferencia de una RNN (izquierda → derecha), la atención permite que cada palabra mire a todas las demás; en «banco» de «me senté en el banco del parque» el vector ya no es el mismo que en «el banco me dio un préstamo», lo que resuelve la polisemia que la bolsa de palabras no podía.

Word2vec con la librería gensim

from gensim.models import Word2Vec
# define training data
sentences = [['this', 'is', 'the', 'first', 'sentence', 'for', 'word2vec'],
             ['this', 'is', 'the', 'second', 'sentence'],
             ['yet', 'another', 'sentence'],
             ['one', 'more', 'sentence'],
             ['and', 'the', 'final', 'sentence']]
# train model
model = Word2Vec(sentences, min_count=1)
# summarize the loaded model
print(model)
# summarize vocabulary
words = list(model.wv.vocab)
print(words)
# access vector for one word
print(model['sentence'])
# save model
model.save('model.bin')
# load model
new_model = Word2Vec.load('model.bin')
print(new_model)
Versión de gensim Este código es de gensim 3.x. En gensim 4 o posterior cambian dos líneas: words = list(model.wv.key_to_index) y print(model.wv['sentence']). min_count=1 hace que no se descarte ninguna palabra aunque aparezca una sola vez (por defecto se ignoran las que aparecen menos de 5 veces).
